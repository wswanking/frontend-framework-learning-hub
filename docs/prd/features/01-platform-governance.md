| 项目 | 内容 |
| --- | --- |

## 目标与边界

建立以仓库文档为事实源的完整交付流程。范围包括上下文、PRD、看板、审核、变更和验收留痕；不接入外部 Jira、GitHub Projects 或企业审批系统。

## 角色与权限

| 角色 | 权限 |
| --- | --- |
| AI | 创建草案、拆解任务、更新证据；不得批准审核门禁。 |
| 产品负责人 | 审核范围、优先级、验收标准与交互取舍。 |
| 技术负责人 | 审核架构、契约、依赖和高风险变更。 |
| 发布负责人 | 审核发布、回滚和最终验收。 |

## 功能与交互

- [工程上下文](../../CONTEXT.md)是进入项目的阅读入口；[协作约定](../../../AGENTS.md)定义 AI 工作循环。
- 需求、任务、Issue 和审核看板均使用唯一编号并互相链接。
- 任何状态从“草案”进入“已批准”前，必须有 `REVIEW-*` 条目和人工结论。
- 每次阶段变化都创建 `CHG-*` 变更记录；每个已完成需求都创建验收记录。

## 业务规则

- AI 仅能将审核状态改为“待审核”；不得写入“通过、驳回、需修改、豁免”。
- 没有关联 `IOT-*` 编号的任务不能进入“进行中”。
- 默认情况下，高严重度 Issue、架构、权限、安全、部署和最终验收需要人工审核；当前用户可用最新明确指令为单次交付授权自动化验收。
- 高严重度 Issue 的严重度变更、关闭和豁免仅限产品负责人或技术负责人；贡献者和发布负责人不能通过降级或关闭该 Issue 清除正式发布阻塞。变更前后任一状态为高严重度时均按此规则校验。

## 验收条件

- Given 新任务无需求编号，When 尝试进入开发，Then 看板标记为阻塞。
- Given AI 识别到跨框架契约风险，When 记录风险，Then 同时创建 Issue 或待审核条目。
- Given 人工审核通过或用户明确授权自动化验收，When 更新审核/验收记录，Then 关联需求可进入下一交付阶段。

## 依赖与风险

依赖所有参与者遵守文档流程；外部工具集成留待后续 ADR。没有用户明确授权时，人工审核长期未响应仍保持阻塞。

## 2026-09-20 实施增量

三端各自增加本地交付记录 Mock 和 `/delivery` 看板，展示当前实际需求进度、权限冲突 Issue 与待审核项，并支持筛选、追溯、任务与 Issue 草案及模拟审核。无需求编号的任务不能进入进行中，指定审核人和原因在服务层校验。浏览器本地记录不写入仓库，也不代表人工审批。完整变更记录、证据归档和 REVIEW-001 仍待实现。验证范围见 [QUALITY](../../architecture/QUALITY.md)。

## 2026-09-20 待审核队列与旧数据修正

三端交付种子补齐 REVIEW-001（工程治理）与 REVIEW-002（Dashboard/地理），让 REVIEW-003 关联领域契约和各业务模块，并记录 Angular PrimeNG 许可证缺口 Issue。设备、规则及实验室需求摘要按当前已实现的浏览器 Mock 更新。旧浏览器存储补入缺失种子，只刷新未被编辑的种子记录；已有人工模拟修订与结论保留。上述条目均为待审核或阻塞，不代表审核结论，完整仓库级变更与验收记录仍待实现。

## 2026-09-20 高严重度 Issue 发布门禁

三端交付服务对高严重度 Issue 的关闭、豁免和降级执行负责人权限校验。贡献者尝试将现有高严重度 Issue 标记为已完成或降为中等严重度时，返回 `FORBIDDEN`，原记录与正式发布阻塞保持不变。该本地 Mock 权限规则不代替 REVIEW 审核和最终验收。

## 2026-09-20 已批准需求范围变更留痕

三端交付看板可编辑需求范围与提交需求状态；服务要求已批准需求的范围变更由产品负责人执行。标题、说明、优先级、验收标准或关联编号变更后，需求自动回到待审核，关联已通过/豁免的模拟审核退回待审核，原结论保留在修订历史，并创建可从追溯链打开的 `CHG-*` 记录。阶段字段变更也创建 `CHG-*`。这些记录仅存在各端浏览器 Mock，仓库级变更记录与正式审核仍待完成。
